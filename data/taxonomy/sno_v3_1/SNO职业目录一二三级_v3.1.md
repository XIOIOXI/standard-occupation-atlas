# SNO 职业一级二级三级目录重设计 v3

本方案用于把招聘记录归入一个主要职业位置。它是基于现有目录重新设计的产品分类初稿，不是国家职业分类标准，也尚未用用户的约两万条数据验证。主目录按工作职责和产出划分；行业、技术、对象、资历与用工形式作为独立标签。职业实际存在交叉，本方案通过明确归类规则取得唯一主归属，而不宣称职业概念完全互斥。

## 一 归类约定

1. 一个原子岗位只有一个二级主归属。一级由二级推导，不能独立另选。跨类别检索使用标签或虚拟入口，不复制主节点。
2. 优先依据实际核心职责，其次依据完整岗位名称。公司行业、专业要求、工具语言、部门名不能单独决定职业。
3. 明确的专业职能优先于“经理、主管、总监、助理”等级别词。销售总监归销售，研发经理归研发；只有跨多个职能承担整体经营责任的岗位归经营管理。
4. 二级通常描述稳定职业方向。不按 Java、C++、Python、银行、汽车、游戏、医疗等语言或行业重复设置职能类别。
5. “通用”节点是有定义的正式类别：确认一级职能，但岗位方向未说明或承担该一级多个方向的综合工作。已有明确方向的岗位不能退回通用节点。
6. 岗位名称和职责冲突时，以主要工作产出为准，记录判断依据。存在两个独立职位时拆分记录并保留原记录 ID；一个兼任职位按主要责任归类，并保留兼任标签。无法确认主要责任时进入待复核队列。
7. 本方案采用不等深目录：有必要的二级细分三级，其余二级直达岗位。不强行凑相同数量的三级。


本版共 32 个一级、262 个二级，其中 79 个二级细分为 204 个三级，其余 183 个二级直达岗位。三级数量是设计结果，尚未经过真实数据覆盖验证。

三级统一沿用主要职责与工作对象规则。没有足够信息时可以停在已明确的二级。选择三级后一级和二级从路径自动推导。同一岗位不能同时落在父节点与子节点，父节点统计包含子节点只是汇总，不新增映射记录。通用二级只处理一级已知、二级未知；具体二级上的直接映射处理二级已知、三级未知。

| 非岗位文本 | 公司名、福利、地点、身份说明、招聘标题等；保留原文但不映射职业 |
| 主责待确认 | 明确兼任多个职能却无法识别主要责任；候选目录与理由一起保留 |
| 目录缺口待扩展 | 已知是什么职业，但现有范围确实未覆盖；汇总后建立具体类别，不能直接强塞通用 |

“所有记录都有处理位置”可以做到；“所有记录都能仅凭名称得到确定职业”无法保证。两者要区分，才不会以错误分类换取表面上的全覆盖。

## 五 推荐标签与映射字段

行业标签：金融、汽车、医疗、互联网、教育、房地产、能源、制造等，可多选。

技术标签：Java、C++、Python、React、PLC、CAD、SQL、LLM 等，可多选。

对象与场景标签：企业客户、个人客户、工业设备、移动端、临床、门店等。

角色与阶段标签：执行、专业管理、助理、实习、培养、学徒；不改主目录。

每条映射建议保存 original_record_id、atomic_role_id、original_title、level1_id、level2_id、level3_id、industry_tags、technology_tags、role_tags、classification_status、evidence、alternative_candidates、taxonomy_version。确定归类的记录只能有一个 level2_id；待复核记录允许为空并保留候选，不自动选第一个。

## 七 两万条数据验证与冻结条件

1. 收到原始数据后，先检查字段、重复记录、多岗位文本和名称完整性，区分招聘记录数与不同职业名称数。
2. 对全部不重复名称做初步覆盖扫描。完全相同名称若职责不同，仍需按记录判断，不能一律共用映射。
3. 逐条按本目录归类，记录通用节点、待复核、缺口与多候选。不要为了清零未分类而增加宽泛类别或随意合并。
4. 集中检查通用节点及目录缺口：判断是真实综合工作、信息不足还是类别缺失。确实缺失的职业增加有明确边界的二级。
5. 对容易交叉的岗位进行成对抽查，并验证同义岗位判断一致。抽查应覆盖主要一级、少数类、长尾名称与歧义名称。
6. 输出明确归类比例、通用归类比例、信息不足比例、缺口比例、多候选比例与抽查错误类型。唯一 ID 只证明没有重复主归属，不能证明语义正确。
7. 将本初稿修订为数据验证版后再冻结，保存规则与迁移表。本轮尚未执行上述数据验证。

建议先以本版目录跑一次覆盖扫描，再决定现有三级需调整及哪些二级需继续拆分。类别数量由职业边界和数据需求决定，不追求平均分配岗位，也不以“其他”数量少作为唯一质量指标。

## 八 三级映射补充规则

1. level2_id 明确且 level3_id 为空，是合法的二级直达映射，不应误计为完全未分类。
2. 只允许选择本二级下的三级。选择三级后由 ID 路径推导父级，禁止父子不匹配。
3. 一个兼任职位涉及两个三级时，按主要职责选择；无主要职责证据但二级一致，可以留在二级并保留候选三级。
4. 不同语言、行业、资历不各建同名三级。例如 Java/Python 后端仍归业务服务开发或服务端基础设施开发。
5. 儿科中医等跨专科记录优先按明确岗位专科，其他临床专科收录在已有范围节点并保留专科标签；真实数据验证后再判断是否需要新增，不能按医院名称猜。
6. 科研、工业研发、AI应用之间仍使用 v2 的主产出规则，不能因为存在更具体三级就跨一级抢收。
7. 三级是否保留取决于真实职业区分与检索需求；如果验证发现边界不稳定，可合并三级而保留二级和标签。
