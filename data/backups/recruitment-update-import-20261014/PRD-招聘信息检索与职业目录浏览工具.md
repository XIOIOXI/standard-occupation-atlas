# PRD：招聘信息检索与职业目录浏览工具

- 文档状态：当前基线与下一阶段需求

## 1. 产品背景与目标

本产品面向求职者，将一份持续更新的校园招聘共享表格转换为更容易浏览和追溯的职业目录。原始表格包含公司、地点、招聘岗位、投递链接等信息，但岗位文本常把多个职位写在同一个单元格中，且不便按职业方向逐层浏览。当前产品的重点是：

- 将已导入招聘记录中的岗位名称拆分为可处理的原子岗位，并保留其原始招聘记录；
- 将有足够依据的岗位放入本地 SNO v3.1 三层职业目录，信息不足或处理异常的岗位单独保留；
- 让用户从职业大类逐级进入二级、三级目录，查看关联的真实招聘记录、地点分布和原始招聘/公告链接；
- 让每一个前端展示的岗位都可回溯到来源记录，而不是只展示脱离来源的统计结论。

当前产品不是通用招聘搜索引擎：没有关键词搜索框、公司/地点/行业筛选、账户体系、在线数据抓取、自动更新、前端上传入口或岗位订阅。它也不向用户承诺岗位仍在招聘中；页面展示的是已导入快照中的来源信息。

前端为 React/Vite 单页应用，当前首页标题为“标准职业图鉴”。它以静态 JSON 作为只读数据源：

开发环境由 Vite 白名单提供该目录中的展示投影、原子岗位来源索引、未分类队列和摘要；构建时复制到 `frontend/dist`。当前页面不调用后端业务 API，不直接读取 SQLite，也不会触发模型分类或数据导入。

## 3. 当前已实现功能

以下以当前 `frontend/src/App.jsx` 及其实际接入的 SNO 展示数据为准。“脚本存在”不等于“用户可在页面操作”。

### 3.1 已实现：职业目录逐级浏览

入口：打开前端首页，即进入“标准职业图鉴”。

操作与结果：

1. 用户在一级职业大类气泡图中拖动、缩放或点击气泡；气泡面积按关联原子岗位数表示。
2. 点击一级气泡进入对应二级职业方向；再点击进入三级职业类别。目录中没有三级子节点的二级类会直接进入该二级下的岗位页。
3. 三级目录即使当前没有关联岗位，也会作为“暂无岗位”的气泡显示，便于了解目录结构。
4. 面包屑、“返回上一级”和“适应”按钮可返回或调整地图视图；鼠标/键盘点击可进入，触屏设备采用先选中、再进入的交互。

限制：这是目录浏览，不是搜索或筛选。一级、二级、三级气泡中的数量是关联原子岗位数，不是去重公司数、招聘人数或职位仍有效数量。

### 3.2 已实现：分类状态切换，但仅覆盖接入的状态

入口：职业图鉴主页面的“P2 · MAPPING STATUS”按钮组。

可操作状态包括“已映射（主归属）”“待复核 / 其他岗位”“多职业待拆分”“目录缺口”“异常原子岗位”。切换后，页面显示相应状态的岗位名称分组列表；点击某一项可进入其来源详情。为保护浏览性能，列表最多展示前 500 项。

当前展示产物中，按关联原子岗位计数：已映射 20,191、待复核 370、多职业待拆分 225。展示投影还保留 451 个未分类队列项，原因包括一般待复核/未分类（335）、原非岗位文本恢复后待映射（13）、多来源跨度未验证（59）、拆分子岗位未分类（18）和映射契约校验失败（26）。

限制：

- 页面状态标签虽包含“目录缺口”和“异常原子岗位”，当前展示产物未提供对应可见项。
- 展示投影中仍有 `non_role_text` 状态数据，但当前状态筛选没有这个入口，因此不能视为前端已经完整提供了“非岗位文本”浏览功能。
- “待复核 / 其他岗位”是保留处理状态，不表示系统已经人工确认其职业归属。

### 3.3 已实现：分类/职业详情与招聘来源追溯

入口：从目录气泡或状态列表点击某个三级类别、二级直达类别、暂存分组，或岗位名称分组。

展示结果：

- 分类页显示当前目录路径、关联原子岗位数和去重后的招聘记录数；
- 标准职业详情页显示关联招聘记录数；
- 两类页面均显示中国省级地点提及分布图；同一条记录如同时含多个可识别地点，可能计入多个省份；
- 页面按来源记录列出公司、企业类型（如有）、地点、从原岗位标题拆出的岗位单元，以及招聘来源/招聘公告链接（如有）；
- 同一来源记录在页面中按 `source_record_id` 去重，仍保留其多个岗位单元和岗位组关联。

限制：地点地图基于内置省/市关键词匹配，未识别的地点不会计入地图；它是“地点提及”可视化，不是精确地理编码。页面不展示完整的学历、专业、截止时间、招聘届次等字段，也不支持在详情页筛选或排序。

### 3.4 部分实现：离线导入、校验、快照与岗位分类

已存在且有当前产物支撑的离线能力如下：

- CSV 导入会校验表头、识别 UTF-8/UTF-8 BOM/GB18030 编码，规范化字段并保留原始行；XLSX 的首个工作表也会进入相同的表头映射与规范化流程。公司名称和招聘岗位同时存在才是记录有效的最低条件。缺行业只影响行业分析资格，缺链接、地点、截止时间、学历或专业不会丢弃记录。
- 导入可生成带源文件校验和、导入时间、源数据更新时间、字段问题、重复状态和分析资格的 SQLite 快照。
- 岗位分组脚本会先保守拆分岗位标题，再在兼容行业范围内分组，保留原始岗位名称、来源记录、公司数和地点数。v2 仅合并经审计为高置信度安全的职业族，其余保留原样。
- SNO v3.1 全量分类脚本具备可恢复执行、批次原始模型响应留存、映射契约校验、非岗位确认、多岗位拆分和子岗位再映射的流程；当前前端展示投影由一次已完成的分类结果构建。

限制：以上能力都不是页面入口。当前用户无法在前端上传文件、执行导入、发起分类、查看导入快照或重试失败项。分类脚本的真实模型调用需要显式命令和密钥，且不能由打开页面触发。

## 4. 当前数据与分类流程

### 4.1 从共享表到导入快照

1. 使用手动提供的 CSV 或 XLSX 运行导入脚本；不抓取招聘网站，也不补抓完整职位描述。
2. 表头映射到标准字段，规范化空值、空白、日期、URL 和岗位/专业文本，同时保存原始列值。
3. 基线快照以公司、岗位、招聘届次、招聘批次、地点和两个链接组成稳定记录身份；同一快照中的重复有效身份会标记为 `duplicate`，而不是删除源行。增量更新另使用不含链接和行号的比较键，避免链接或排序变化重复导入。
4. 每条记录分别保存 `record_status`、市场分析资格、行业分析资格和字段级问题。有效性与分析资格不同：缺公司或招聘岗位无效；缺行业仍可做市场分析但不进入行业分段。

### 4.2 岗位拆分、分组与来源保留

1. 对可用于市场分析且非重复的招聘记录，按当前的保守标题拆分规则生成通过质量门槛的岗位单元（原子岗位）。不通过的单元不会强行进入分组。
2. 每个原子岗位都保留来源记录 ID、原始完整岗位标题、拆分后的岗位单元、公司、行业、地点、届次、批次、专业和学历上下文。
3. v1 按“已确认的旧目录职业身份或规范化岗位单元 + 兼容行业上下文”聚合；v2 只对安全审计为高置信度的职业族进一步合并，且禁止跨行业上下文合并。
4. 当前 v1 结果为 15,846 个岗位组；v2 为 15,622 个岗位组。两版均保留所有来源原子岗位和招聘记录血缘，不用标准职业名称覆盖原始岗位标题。

### 4.3 映射到 SNO v3.1 目录

1. 当前展示采用 SNO v3.1 本地目录；每个原子岗位只允许一个主二级归属，三级归属是可选的，不能因信息不足而猜测三级。
2. 分类以岗位标题为主要依据，并对模型结果执行合法目录 ID、目标层级、三级证据和候选类别的结构校验。目录中停用的 ID 不可再映射。
3. 映射结果包含 `mapped`、`review`、`taxonomy_gap`、`multi_role`、`non_role_text` 等状态。`mapped` 才进入正式目录气泡；仅能确认到二级的岗位允许直接落在二级，不伪造三级类别。
4. 分类运行包含独立复核。复核只有在给出合法、明确的纠正目标时才改写有效结果；原始模型输出、提示版本、目录版本、批次文件和失败信息保留在离线产物中。

### 4.4 多岗位、待确认和非岗位文本

- **多岗位文本**：只有确认是可验证的多岗位情形时，才按原文本中的字符跨度拆成子岗位；每个子岗位重新映射。原组合文本不再作为正式展示项，来源记录不会复制或丢失。无法验证拆分跨度的，保留为多岗位待拆分。
- **待确认/目录缺口**：信息不足、候选目录不确定、真实目录缺口或映射校验失败时，不自动创建目录节点、不强行归类；保留在未分类队列，带原因、状态和来源记录/原子岗位 ID。
- **非岗位文本**：经确认的非岗位文本从正式展示排除但不删除源记录；无法确认的文本会保留待处理。当前页面没有独立的非岗位文本浏览入口。

## 5. 新增岗位更新（已实现，等待真实新版文件验证）

本章描述已落地的本地处理能力；当前尚未收到真实新版文件，因此没有真实新增数量或真实批次可展示。

### 5.1 使用方式与边界

1. 运营者手动从飞书下载同一份招聘文件（XLSX 或 CSV）后，直接提供给 Codex；由 Codex 运行本地脚本处理。XLSX 读取后进入与 CSV 相同的表头映射、规范化和校验逻辑。
2. 不开发面向求职者或运营者的前端上传入口；不自动下载飞书文件；不设置每日或其他定时任务。
3. 以当前已导入的源数据为固定基线，仅识别新文件中相对于该基线的新增招聘记录或新增岗位。稳定招聘记录比较沿用现有身份语义，但新增比较不得把链接、行号或文件排序作为身份；链接变化本身不算新增。
4. 同一企业的不同岗位应识别为新增；同一招聘记录追加岗位时，只识别新增的原子岗位。除岗位新增外，其他已有内容修改、删除、失效或下架暂不处理。

### 5.2 增量处理流程

1. 对运营者提供的新文件做与当前 CSV 相同的表头校验、字段规范化和质量问题记录；保存本次文件校验和、导入时间、基线标识、处理版本和批次状态。
2. 用不含链接和行号的招聘记录比较键识别新增记录；再按不含链接和行号的原子岗位比较键识别岗位。文件行顺序、排序变化、链接变化和无关列顺序变化不得造成新增。同一记录追加的岗位必须进入原子岗位比较，因此只产生追加部分的新增岗位。
3. 新增岗位复用现有岗位标题拆分、质量门槛、分类契约和 SNO v3.1 映射流程。已见过的同名岗位可复用已持久化、可追溯的分类结果；未见岗位由显式本地模型批次处理。映射有充分依据的进入对应目录；信息不足、拆分不可靠、目录缺口或校验失败的保留待确认，不能编造目录归属。
4. 批次需要保存新增、已归类、待确认、失败、跳过重复等逐条结果及来源血缘。失败条目可在同一批次或后续明确重试中重跑；成功且已存在的项不得重复导入或重复分类。
5. 批次处理完成后，导出供当前前端读取的批次展示数据。前端以只读叠加方式合并已归类岗位到主职业目录对应节点：更新气泡数量、关联招聘记录、来源详情和地点分布；待确认和失败岗位仍走现有待复核与异常展示路径。基础展示投影和历史分类结果不被改写。

当前实现说明：`scripts/process_recruitment_update.py` 接受一个手动提供的 CSV 或 XLSX，默认仅复用已有同名岗位分类；指定 `--mapping-mode model` 时才对未见标题调用现有版本化 SNO 映射执行器。批次和原子岗位处理记录保存到 `data/processed/recruitment_updates.sqlite`，并导出 `update_batches.json` 给前端。`SnoExplorer` 在读取基础投影时按原子岗位键去重叠加批次数据，来源详情索引也同时读取该批次数据。`--retry-failed <批次 ID> --mapping-mode model` 仅重试失败原子岗位。此命令不会自动下载、上传或定时运行。

示例（由 Codex 在收到文件后执行）：

```powershell
$env:PYTHONPATH = "backend"
.\.venv-role-vectors\Scripts\python.exe scripts\process_recruitment_update.py <飞书下载的文件.xlsx> --mapping-mode model
```

### 5.3 前端展示与批次通知

1. 在现有图鉴顶部提供“更新”入口；有批次时可进入“本批新增岗位”列表，展示已归类、待确认和失败状态，以及每个岗位的企业、地点、目录路径或处理原因。已归类岗位同时会被叠加到既有目录气泡、分类/职业详情、招聘来源与地点分布中；批次列表仍保留为本次更新入口。
2. 本批处理完成后显示类似手机消息通知的小弹框，至少汇报：新增原子岗位、涉及招聘记录、已归类、待确认、失败数量，并提供“查看详情”入口。已归类、待确认、失败均以同一原子岗位口径计数。
3. 通知的已读/关闭状态按批次持久化；同一批次通知读过或关闭后，不在后续打开页面时重复弹出。新批次可以产生新的通知。
4. 通知计数必须由该批次实际持久化结果确定，不能由前端临时猜测或模型文本生成。

|---|---|
| 首页与数据读取 | 打开前端首页后能读取展示投影；读取失败时显示明确错误，而不是空白页。 |
| 目录浏览 | 能从一级进入二级、三级（或二级直达页），并通过面包屑/返回按钮回到上级。 |
| 数量口径 | 气泡和状态栏数量以关联原子岗位数计算；三级空目录节点显示为暂无岗位，不伪造岗位。 |
| 状态分流 | 已映射、待复核、多职业待拆分等已接入状态可切换并展示对应岗位组；正式目录不混入未确认项。 |
| 来源追溯 | 从分类或岗位详情可看到关联公司、地点、拆分岗位单元，存在链接时可打开招聘来源/公告。 |
| 地点图 | 页面对可识别的地点提及生成省级分布；无法识别地点不影响招聘记录本身的显示。 |
| 数据保真 | 从页面项可沿 `source_atomic_unit_id` / `source_record_id` 回到当前展示来源索引；原始岗位标题未被标准职业名覆盖。 |
| 未确认数据 | 未分类队列保留待确认、多岗位、目录缺口或校验失败项；不能因展示需要自动创建 SNO 类别。 |

### 6.2 已实现新增功能验收标准

| 验收项 | 可验证标准 |
|---|---|
| 基线正确 | 给定当前基线和一份新文件，只将不在基线中的稳定招聘记录/岗位标为新增；基线文件自身再次处理时新增数为 0。链接和行号不得参与增量身份。 |
| 排序不影响结果 | 仅重排行、调整无关列顺序、改变投递/公告链接或重新导出内容等价的文件，结果为 0 新增、0 重复导入。 |
| 重复运行防护 | 同一文件或相同内容批次重复运行，不产生新的招聘记录、原子岗位、分类项或重复通知；系统可定位已有批次。 |
| 新岗位分类 | 新增岗位使用与现有数据相同的拆分和 SNO v3.1 映射规则；已归类项有合法目录路径，证据不足项进入待确认，不强行分类。 |
| 前端可检索/浏览 | 成功归类的新岗位能通过“本批新增岗位”入口和主目录对应节点找到；目录数量、分类/职业详情、来源记录和地点分布均包含该新增岗位，且不重复计数。 |
| 批次详情 | 批次详情中新增、已归类、待确认、失败和跳过重复的条目数可核对到持久化逐条结果。 |
| 通知一致性 | 通知中的新增原子岗位、涉及招聘记录、已归类、待确认、失败数量与该批次详情和持久化统计完全一致；点击详情进入对应批次。 |
| 通知去重 | 同一批次通知关闭或标记已读后，刷新/再次进入页面不再弹出；新批次仍可独立提示。 |
| 失败重试 | 失败条目可被明确选择重试；已成功或已跳过的条目不因重试重复导入，重试结果和原因可追溯。 |
| 不处理既有变更 | 新文件中仅对已有岗位的修改、删除或下架不计为新增，也不改变基线现有展示数据。 |

## 7. 范围与待确认事项

### 7.1 本阶段范围

- 维护现有静态只读职业图鉴及其来源追溯；
- 为手动提供的新飞书同源文件提供可重复、可审计的本地增量处理；
- 将本批新增、已归类、待确认和失败结果接入当前前端，并提供按批次去重的浏览器本地通知。

### 7.2 暂不做

- 前端上传、自动下载飞书、爬取招聘网站、定时或每日更新；
- 既有岗位的修改检测、删除检测、下架检测和历史版本对比；
- 全文搜索、复杂筛选、账号系统、收藏、订阅、真实移动端推送；
- 更改 SNO v3.1 目录、从招聘数据自动新增目录节点或覆盖原始岗位标题；
- 将当前未接入页面的课程—技能、推断和旧市场地图产物纳入本次新增岗位功能。

### 7.3 已知限制与后续确认

1. **更新判定边界**：已经确定链接变化、行号和排序不算新增；当前仍不对地点、届次、批次、公司名称或岗位文本的既有内容修改做更新/删除语义处理。实施中会以“不重复导入”为优先，不把这类变化自动解释为更新。
2. **运行入口与权限**：已确定由 Codex 在项目工作区运行本地脚本，不建设上传 API 或管理页面。
3. **通知持久化位置**：已确定批次及处理记录持久化在本地数据层；通知已读/关闭状态只需在当前浏览器持久化。
4. **新增统计**：已确定通知主数量为新增原子岗位数，并补充涉及招聘记录数；归类、待确认、失败与主数量采用同一原子岗位口径。

## 8. 实现一致性原则

- 以原始招聘记录和来源 ID 为证据根；标准目录只描述分类，不替代原始招聘岗位标题。
- 目录映射、拆分、分类版本、批次和失败原因必须可追溯；不能在页面打开时运行模型或更改数据。
- 统计数量由已持久化记录确定，模型只能参与候选分类，不能生成或修改数量。
- 任何将来发现“代码存在但页面未接入”的能力，都必须在本文档标为“部分实现”或“未实现”，直到用户可验证其完整路径。
