# Job-title Splitting Audit

This audit reviews the deterministic `split_title_units()` logic used by Taxonomy Coverage Analysis. It does not modify the Reference Taxonomy, recruitment records, mapping rules, candidate pool, frontend, CSV importer, or splitter implementation.

## Scope

- Snapshot: `24923444-9eb3-4f4e-a2eb-e611b964287b`
- Recruitment records audited: 6,163
- Distinct raw job-title fields: 5,919
- Generated job-title units: 36,108
- Average units per recruitment record: 5.86

## Current splitting logic

Current implementation steps:

1. Collapse all whitespace in `raw_job_title` to a single space and trim edges.
2. If the title contains `:` or `：`, return the whole cleaned title as one unit. This protects fields where a colon introduces requirements or majors.
3. Otherwise split only on `、`, `,`, `，`, `;`, `；`, or newline.
4. Trim spaces and trailing/leading ` ，,;；` from each unit, then drop empty units.

The current splitter does not split on `/`, `|`, brackets, parentheses, hyphen, middle dot, spaces, Chinese enumeration markers such as `1.` or `（一）`, or job-family words. Any over-splitting therefore mostly comes from broad comma/list delimiters in mixed job-title fields rather than from semantic decomposition of a single title.

## Over-splitting risk

The splitter is syntactically narrow, but the source field often contains broad recruitment menus rather than one title. Splitting on list delimiters creates many fragments that look like locations, education requirements, majors, job families, departments, or business directions. The largest risk is not splitting a single semantic title like `人工智能算法研发工程师`; that remains one unit unless it contains a configured delimiter. The larger risk is treating every comma-separated fragment in long mixed fields as a standalone occupation candidate.

The 36,108 unit count is reproducible, but it should not be treated as 36,108 trustworthy occupation mentions. Based on audit flags, roughly 13,025 generated units or unsplit mixed fields need review before being used for taxonomy expansion. The reliable evidence unit should remain source records plus carefully reviewed candidate titles, not raw split-unit count alone.

## Recommended deterministic rule changes

These are recommendations only; this audit did not implement them.

1. Add a `split_reason` and `split_confidence` field to every generated unit so downstream coverage can distinguish explicit position lists from weak fragments.
2. Preserve comma/list splitting, but suppress candidate generation for units that lack a role marker unless the unit exactly matches a Reference Taxonomy occupation or alias.
3. Add a high-unit-count review gate: records producing more than 5 or 10 units should be reviewed before their units enter taxonomy expansion decisions.
4. Add fragment filters for locations, education levels, connectors, departments, business lines, education/major requirement text, and generic category labels.
5. Prevent delimiter splitting inside parentheses when the parenthetical looks like city, education, or requirement context.
6. Consider title-list reconstruction rules for patterns such as `软件开发、测试、运维工程师`, where the final suffix may apply to earlier fragments. This should be deterministic and separately tested.
7. Keep the current colon protection, but refine it so a colon inside a parenthetical qualifier does not automatically block splitting the entire field.

## Conclusion

**C. There is clear over-splitting risk. Fix or gate the splitter output before rerunning Coverage Analysis for taxonomy expansion.**

Reason: the splitter is simple and reproducible, but the source job-title field frequently contains mixed lists. The expansion from 6,163 records to 36,108 units is driven by list delimiters, and many generated units are locations, education markers, majors, category labels, departments, or descriptive text rather than standalone occupations. Continuing to expand Reference Taxonomy directly from this candidate pool would likely add noisy or wrongly scoped occupation candidates.
