# PRD：应届生在线求职工具台

- 文档状态：当前基线、已实现能力与后续规划
- 更新时间：2026-10-21
- 维护约定：后续新增或调整功能时，必须同步更新本文档，并以实际运行页面、数据产物和脚本为准。

## 1. 产品背景与目标

本产品面向应届生，将零散、持续更新的校园招聘信息转换为更容易浏览、追溯和后续扩展为求职决策支持的在线工具台。原始表格包含公司、地点、招聘岗位、投递链接等信息，但岗位文本常把多个职位写在同一个单元格中，且不便按职业方向逐层浏览。当前产品的重点是：

- 将已导入招聘记录中的岗位名称拆分为可处理的原子岗位，并保留其原始招聘记录；
- 将有足够依据的岗位放入本地 SNO v3.1 三层职业目录，信息不足或处理异常的岗位单独保留；
- 让用户从职业大类逐级进入二级、三级目录，查看关联的真实招聘记录、地点分布和原始招聘/公告链接；
- 让每一个前端展示的岗位都可回溯到来源记录，而不是只展示脱离来源的统计结论；
- 由本机受限招聘更新 Agent 处理运营者手动上传的新 CSV/XLSX：程序负责比较、去重、校验和写入，LLM 只在受限工具内决定复用、分类、复核或待确认。

当前产品尚不是通用招聘搜索引擎：没有关键词搜索框、公司/地点/行业筛选、账户体系、在线数据抓取、自动更新或岗位订阅。它也不向用户承诺岗位仍在招聘中；页面展示的是已导入快照中的来源信息。仅供本机运营者使用的上传管理入口已实现，不面向普通求职者开放。

### 2.2 现有页面的运行方式

前端为 React/Vite 单页应用，当前首页标题为“标准职业图鉴”。它以静态 JSON 作为只读数据源：

`data/processed/record_role_classification_v1/full_drafts/sno_v31_reasonable_primary_v4_display/`

开发环境由 Vite 白名单提供该目录中的展示投影、原子岗位来源索引、未分类队列和摘要；构建时复制到 `frontend/dist`。当前页面不调用后端业务 API，不直接读取 SQLite，也不会触发模型分类或数据导入。

## 3. 当前已实现功能

以下以当前 `frontend/src/App.jsx` 及其实际接入的 SNO 展示数据为准。“脚本存在”不等于“用户可在页面操作”。

### 3.1 已实现：职业目录逐级浏览

入口：打开前端首页，即进入“标准职业图鉴”。

操作与结果：

1. 用户在一级职业大类气泡图中拖动、缩放或点击气泡；气泡面积按关联原子岗位数表示。
2. 点击一级气泡进入对应二级职业方向；桌面端以自然过渡将左侧目录信息栏压缩至不超过 180px 的窄栏（标题、状态项字号同步缩小），右侧气泡画布扩展为主区域（至少占当前视口宽度的三分之二），且不得出现横向页面溢出；再点击进入三级职业类别时沿用该画布尺寸。目录中没有三级子节点的二级类会直接进入该二级下的岗位页；移动端保持纵向布局。
3. 三级目录即使当前没有关联岗位，也会作为“暂无岗位”的气泡显示，便于了解目录结构。
4. 面包屑、“返回上一级”和“适应”按钮可返回或调整地图视图；鼠标/键盘点击可进入，触屏设备采用先选中、再进入的交互。

限制：这是目录浏览，不是搜索或筛选。一级、二级、三级气泡中的数量是关联原子岗位数，不是去重公司数、招聘人数或职位仍有效数量。

### 3.2 已实现：分类状态切换，但仅覆盖接入的状态

入口：职业图鉴主页面的“P2 · MAPPING STATUS”按钮组。

可操作状态包括“已映射（主归属）”“待复核 / 其他岗位”“多职业待拆分”“目录缺口”“异常原子岗位”。切换后，页面显示相应状态的岗位名称分组列表；点击某一项可进入其来源详情。为保护浏览性能，列表最多展示前 500 项。

当前展示产物中，按关联原子岗位计数：已映射 20,191、待复核 370、多职业待拆分 225。展示投影还保留 451 个未分类队列项，原因包括一般待复核/未分类（335）、原非岗位文本恢复后待映射（13）、多来源跨度未验证（59）、拆分子岗位未分类（18）和映射契约校验失败（26）。

限制：

- 页面状态标签虽包含“目录缺口”和“异常原子岗位”，当前展示产物未提供对应可见项。
- 展示投影中仍有 `non_role_text` 状态数据，但当前状态筛选没有这个入口，因此不能视为前端已经完整提供了“非岗位文本”浏览功能。
- “待复核 / 其他岗位”是保留处理状态，不表示系统已经人工确认其职业归属。

### 3.3 已实现：分类/职业详情与招聘来源追溯

入口：从目录气泡或状态列表点击某个三级类别、二级直达类别、暂存分组，或岗位名称分组。

展示结果：

- 分类页显示当前目录路径、关联原子岗位数和去重后的招聘记录数；
- 标准职业详情页显示关联招聘记录数；
- 两类页面均显示中国省级地点提及分布图；同一条记录如同时含多个可识别地点，可能计入多个省份；
- 页面按来源记录列出公司、企业类型（如有）、地点、从原岗位标题拆出的岗位单元，以及招聘来源/招聘公告链接（如有）；
- 同一来源记录在页面中按 `source_record_id` 去重，仍保留其多个岗位单元和岗位组关联。

限制：地点地图基于内置省/市关键词匹配，未识别的地点不会计入地图；它是“地点提及”可视化，不是精确地理编码。页面不展示完整的学历、专业、截止时间、招聘届次等字段，也不支持在详情页筛选或排序。

### 3.4 部分实现：离线导入、校验、快照与岗位分类

已存在且有当前产物支撑的离线能力如下：

- CSV 导入会校验表头、识别 UTF-8/UTF-8 BOM/GB18030 编码，规范化字段并保留原始行；XLSX 的首个工作表也会进入相同的表头映射与规范化流程。公司名称和招聘岗位同时存在才是记录有效的最低条件。缺行业只影响行业分析资格，缺链接、地点、截止时间、学历或专业不会丢弃记录。
- 导入可生成带源文件校验和、导入时间、源数据更新时间、字段问题、重复状态和分析资格的 SQLite 快照。
- 岗位分组脚本会先保守拆分岗位标题，再在兼容行业范围内分组，保留原始岗位名称、来源记录、公司数和地点数。v2 仅合并经审计为高置信度安全的职业族，其余保留原样。
- SNO v3.1 全量分类脚本具备可恢复执行、批次原始模型响应留存、映射契约校验、非岗位确认、多岗位拆分和子岗位再映射的流程；当前前端展示投影由一次已完成的分类结果构建。

限制：导入和模型分类不是普通求职者页面功能。仅本机运营者可通过“管理更新”入口上传文件、执行导入和发起分类；页面打开本身不会触发模型调用。失败或待确认项的选择性重试仍是后续管理能力。

### 3.5 已实现：每日新增岗位日历

入口：图鉴顶部的“每日新增”按钮。

操作与结果：

1. 页面读取构建时生成的只读日历索引，按招聘源保留的原始更新时间浏览岗位；当前覆盖 2026-08-01 起的已生效基线与后续补录数据。
2. 月度日历中有岗位的日期显示数量气泡；点击日期后仅展示该日的岗位。
3. 日内岗位列表复用职业详情（四级页）的“真实招聘岗位记录与来源”组件：按招聘记录合并岗位名称，展示企业、企业类型、地点、岗位单元及招聘来源/公告链接（如有）。
4. 缺少原始更新时间的记录不会使用导入日期或推测发布日期替代，也不会被归入任意日期。

限制：日历是静态展示索引，不提供前端上传、自动下载、定时更新、全文搜索或额外筛选。它展示的是按原始更新时间检索到的岗位，并不代表职位仍在招聘或首次发布于该日。

## 4. 当前数据与分类流程

### 4.1 从共享表到导入快照

1. 使用手动提供的 CSV 或 XLSX 运行导入脚本；不抓取招聘网站，也不补抓完整职位描述。
2. 表头映射到标准字段，规范化空值、空白、日期、URL 和岗位/专业文本，同时保存原始列值。
3. 基线快照以公司、岗位、招聘届次、招聘批次、地点和两个链接组成稳定记录身份；同一快照中的重复有效身份会标记为 `duplicate`，而不是删除源行。增量更新另使用不含链接和行号的比较键，避免链接或排序变化重复导入。
4. 每条记录分别保存 `record_status`、市场分析资格、行业分析资格和字段级问题。有效性与分析资格不同：缺公司或招聘岗位无效；缺行业仍可做市场分析但不进入行业分段。

### 4.2 岗位拆分、分组与来源保留

1. 对可用于市场分析且非重复的招聘记录，按当前的保守标题拆分规则生成通过质量门槛的岗位单元（原子岗位）。不通过的单元不会强行进入分组。
2. 每个原子岗位都保留来源记录 ID、原始完整岗位标题、拆分后的岗位单元、公司、行业、地点、届次、批次、专业和学历上下文。
3. v1 按“已确认的旧目录职业身份或规范化岗位单元 + 兼容行业上下文”聚合；v2 只对安全审计为高置信度的职业族进一步合并，且禁止跨行业上下文合并。
4. 当前 v1 结果为 15,846 个岗位组；v2 为 15,622 个岗位组。两版均保留所有来源原子岗位和招聘记录血缘，不用标准职业名称覆盖原始岗位标题。

### 4.3 映射到 SNO v3.1 目录

1. 当前展示采用 SNO v3.1 本地目录；每个原子岗位只允许一个主二级归属，三级归属是可选的，不能因信息不足而猜测三级。
2. 分类以岗位标题为主要依据，并对模型结果执行合法目录 ID、目标层级、三级证据和候选类别的结构校验。目录中停用的 ID 不可再映射。
3. 映射结果包含 `mapped`、`review`、`taxonomy_gap`、`multi_role`、`non_role_text` 等状态。`mapped` 才进入正式目录气泡；仅能确认到二级的岗位允许直接落在二级，不伪造三级类别。
4. 分类运行包含独立复核。复核只有在给出合法、明确的纠正目标时才改写有效结果；原始模型输出、提示版本、目录版本、批次文件和失败信息保留在离线产物中。

### 4.4 多岗位、待确认和非岗位文本

- **多岗位文本**：只有确认是可验证的多岗位情形时，才按原文本中的字符跨度拆成子岗位；每个子岗位重新映射。原组合文本不再作为正式展示项，来源记录不会复制或丢失。无法验证拆分跨度的，保留为多岗位待拆分。
- **待确认/目录缺口**：信息不足、候选目录不确定、真实目录缺口或映射校验失败时，不自动创建目录节点、不强行归类；保留在未分类队列，带原因、状态和来源记录/原子岗位 ID。
- **非岗位文本**：经确认的非岗位文本从正式展示排除但不删除源记录；无法确认的文本会保留待处理。当前页面没有独立的非岗位文本浏览入口。

## 5. 新增岗位更新 Agent（已实现并完成正式小预算验证）

本章描述已落地的本地处理能力与验证边界。它是单一、受限的招聘更新 Agent，而不是具有任意代码执行或目录修改权限的通用 Agent。

### 5.1 使用方式与边界

1. 运营者手动从飞书下载同一份招聘文件（XLSX 或 CSV）后，在项目目录执行本地启动命令即可处理；不依赖 Codex 对话。XLSX 读取后进入与 CSV 相同的表头映射、规范化和校验逻辑。
2. 已提供仅面向本机运营者的前端上传入口；不自动下载飞书文件；不设置每日或其他定时任务。普通求职者不接触 API Key、上传管理或模型预算。
3. 以所有已持久化导入快照和全部历史更新批次为比较集合，仅识别新文件中相对于该集合的新增招聘记录或新增岗位。稳定招聘记录比较沿用现有身份语义，但新增比较不得把链接、行号或文件排序作为身份；链接变化本身不算新增。原始更新时间仅用于用户日期展示和辅助筛选，不能单独决定新增。
4. 同一企业的不同岗位应识别为新增；同一招聘记录追加岗位时，只识别新增的原子岗位。除岗位新增外，其他已有内容修改、删除、失效或下架暂不处理。

### 5.2 增量处理流程

1. 对运营者提供的新文件做与当前 CSV 相同的表头校验、字段规范化和质量问题记录；保存本次文件校验和、导入时间、基线标识、处理版本和批次状态。
2. 用不含链接和行号的招聘记录比较键识别新增记录；再按不含链接和行号的原子岗位比较键识别岗位。文件行顺序、排序变化、链接变化和无关列顺序变化不得造成新增。同一记录追加的岗位必须进入原子岗位比较，因此只产生追加部分的新增岗位。
3. 新增岗位复用现有岗位标题拆分、质量门槛、分类契约和 SNO v3.1 映射流程。只有职业身份足够具体的已见标题可复用已持久化、可追溯的分类结果；“工程师”“产品经理”“管培生”等泛化名称不得仅因同名继承分类，必须带公司、行业、原始组合岗位、地点、届次/批次等最小上下文进入显式模型批次。未见岗位也仅发送该岗位的必要上下文、版本化分类规则和 SNO 目录，绝不发送两份全量文件。映射有充分依据的进入对应目录；信息不足、拆分不可靠、目录缺口或校验失败的保留待确认，不能编造目录归属。
4. 批次需要保存新增、已归类、待确认、失败、跳过重复等逐条结果及来源血缘。模型响应先校验 JSON 包络、返回岗位 ID、目录 ID、层级和三级证据；无效结果保留原始响应后可发起一次受预算约束的修正请求，仍失败则待确认并继续其他岗位。失败条目可在同一批次或后续明确重试中重跑；成功、待确认或失败且已存在的项不得因新文件再次出现而重复导入或重复分类。
5. 批次处理完成后，导出供当前前端读取的批次展示数据。前端以只读叠加方式合并已归类岗位到主职业目录对应节点：更新气泡数量、关联招聘记录、来源详情和地点分布；待确认和失败岗位仍走现有待复核与异常展示路径。基础展示投影和历史分类结果不被改写。

当前实现说明：`scripts/process_recruitment_update.py` 接受手动提供的 CSV 或 XLSX；`--mapping-mode model` 可调用现有 SNO 映射执行器。单次运行的模型请求统一由共享账本记录并保守预留预算，细节和验证边界见第 5.4 节。`update_batches.json` 作为前端只读输入，失败项目可显式重试；命令不会自动下载或定时运行。

### 固定程序与 LLM 的明确边界

这不是具备任意权限的自治式 Agent。已实现的是**受限工具 Agent**：它对每个新增岗位读取上一步工具结果，并在允许动作内选择下一步；文件、目录和数据写入仍由固定程序掌控。无密钥模式使用可测试的模拟决策器，不会冒充 LLM。配置 DeepSeek 后，决策器才会由 LLM 返回受限动作：

| 固定程序控制 | LLM 在模型模式中可做的受限判断 |
|---|---|
| 文件格式/字段校验、源文件和原子岗位去重、标题拆分、所有已导入快照比较、运行锁、预算停止、JSON/ID/层级校验、持久化、统计、日历/目录/通知刷新 | 对单个新增岗位判断是否应保持单项、是否存在明确多岗位语义、提出 SNO 目录候选或待确认理由、对一次无效结构结果作修正 |
| 新增数量、记录有效性、目录可用 ID、是否导入、费用账本和最终展示数量 | 不得读取两份全量文件、不得生成统计数、不得创建目录节点、不得绕过证据/校验；可在单岗位上从复用、请求拆分、分类、修正或待确认中选择下一步 |

程序提供每岗位 6 次工具调用和一次 Agent 修正的限制；分类和复用都必须经程序的结构、目录、层级和证据闸门。模拟测试及先前真实运行均观察到工具结果驱动下一步；真实修正仍未验证。语义合理性仍需要岗位职责证据，而非仅凭结构正确。

### DeepSeek 配置与真实验证状态

在项目根目录的 `.env` 中增加一行 `DEEPSEEK_API_KEY=...`，或在启动本机 API 的同一终端设置环境变量 `DEEPSEEK_API_KEY`。密钥绝不应写入前端代码、提交到仓库或粘贴到页面。隔离验证使用 `--sandbox-dir` 与共享预算；一次正式运行的全部决策、分类和复核共享同一预算账本。

## 7. 范围与待确认事项

### 7.1 本阶段范围

- 面向应届生维护职业目录、来源追溯和每日新增岗位浏览；
- 为运营者手动提供的新飞书同源文件提供可重复、可审计的本地增量处理；
- 将已归类和待确认的新岗位接入当前前端：用户按原始更新时间浏览每日新增；内部批次仅用于去重、审计和浏览器本地通知；
- 通过单一、受限的招聘更新 Agent 决定新增岗位的安全复用、分类、复核或待确认；程序始终控制数据读取、校验、写入、预算与统计；
- 支持已核验的人工映射包本地回填，并保留原始更新时间、原子岗位 ID 血缘、重复合并与多岗位拆分审计信息。

### 7.2 暂不做

- 招聘批次、学历、专业等扩展筛选；
- 简历上传解析、简历—岗位匹配、投递优先级或补强建议；
- 对话式求职助手、RAG/知识库问答；
- 自动下载飞书、爬取招聘网站、定时或每日更新；
- 既有岗位的修改检测、删除检测、下架检测和历史版本对比；
- 账号系统、收藏、订阅、真实移动端推送；
- 更改 SNO v3.1 目录、从招聘数据自动新增目录节点或覆盖原始岗位标题；
- 将大学课程、学习成果、课程—技能对比、课程推荐纳入当前求职工具台 MVP。

### 7.3 分步路线图：应届生求职工作台与求职助手

本路线图不改变当前招聘更新 Agent 的职责。工作台先提供可靠、可解释的确定性工具；求职助手随后仅通过受限工具组织这些能力，不直接读写数据库、不执行任意代码、不把模型推断伪装成招聘事实。

#### 阶段 1：岗位搜索与筛选（工作台底座，已实现基础版）

**目标**：让应届生无需理解 SNO 目录，也能快速从已导入、可追溯的岗位中找到候选岗位。

- 已提供岗位关键词、职业方向（关键词匹配目录路径）、公司、地点、行业、届次、分类状态、源更新时间、截止日期与排序；筛选组合使用确定性查询，不调用 LLM。招聘批次、学历、专业等扩展筛选仍未实现。
- 每个结果显示原始岗位名、拆分后的岗位单元、公司、地点、原始更新时间、截止时间、来源链接、目录归属与分类状态；待确认岗位必须明确标注，不混入已确认归类结果。
- 搜索索引只基于已持久化的原始字段与已校验分类；结果始终可回到 `source_record_id` 与来源链接。
- **已验证**：搜索索引由招聘快照、原子岗位证据、目录归属和增量批次确定性生成，共 22,282 条搜索项；前端构建通过。搜索索引在每次正式增量处理完成后自动刷新。
- **待验证**：浏览器人工回归，包括多条件组合、移动端布局与大数据量加载体验。

#### 阶段 2：个人求职看板（收藏、投递状态与截止提醒）

**目标**：把“看到岗位”变成可管理的投递行动，但不把个人状态误写回公共招聘数据。

- 支持收藏、隐藏、投递状态（待评估、准备中、已投递、笔试、面试、终止）和个人备注；个人状态独立于公共岗位、目录和招聘来源。
- 第一版可采用浏览器本地持久化，明确提示其仅在当前设备/浏览器可见；跨设备同步、账号和云端存储必须另行设计权限与数据删除机制后才可上线。
- 截止提醒只针对来源中明确保存的截止时间；没有截止时间时不得编造提醒日期。浏览器本地提醒不能保证用户关闭浏览器后仍触发，可靠推送需后续账号与服务端能力。
- **验收**：用户的收藏/投递状态不影响其他用户或岗位统计；删除个人数据不删除公共岗位；提醒内容能回到原始截止时间与来源记录。

#### 阶段 3：岗位解释与比较助手（首个面向用户的 Agent）

**目标**：让用户能用自然语言理解岗位，但答案始终有数据范围、来源和不确定性。

- Agent 只可调用受限只读工具：`search_jobs`、`filter_jobs`、`get_job_detail`、`compare_jobs`、`get_daily_updates`、`get_saved_jobs`。工具返回结构化、已持久化数据，模型不得自行编造岗位、截止时间、公司状态或统计量。
- 典型问题包括：“本周上海有哪些数据分析新增？”“产品岗和运营岗有什么区别？”“我收藏的岗位哪些截止更近？”“这家公司这一批有哪些岗位？”
- 每次回复应说明使用了哪些筛选条件，引用来源记录或岗位卡片；数据不足时回答“无法从已导入数据确认”。不展示模型内部思考。
- **验收**：工具参数、来源 ID、返回数量与答案中的事实可核对；无工具结果时不输出具体岗位结论；提示注入、越权检索和任意代码执行请求被拒绝或安全降级。

#### 阶段 4：简历解析与岗位匹配（隐私优先）

**目标**：在用户明确授权的前提下，将个人经历与已导入岗位做可解释的匹配和投递排序。

- 上传前说明将读取的简历内容、保存位置、保留期限和删除方式；默认不将简历用于训练，不把简历发送给未说明的第三方服务。
- 程序先提取教育、项目、技能、实习、意向城市和意向方向等结构化事实；模型只能补充候选解释，不能把未出现的经历、技能或工作经历当成事实。
- 匹配分为确定性条件（地点、届次、学历、截止时间、明确专业/技能）与候选语义匹配；界面必须区分“岗位明确要求”“简历直接证据”“模型候选判断”。
- Agent 可调用 `parse_resume`、`match_resume_to_jobs`、`explain_match`、`prioritize_applications`，但不能自动投递、伪造经历或替用户修改简历。
- **验收**：用户可查看每个匹配理由与缺失依据，可删除简历及衍生结果；弱证据岗位不会被描述为“高度匹配”；同一输入和版本产生可复现的基础分数。

#### 阶段 5：求职行动助手与评估运营

**目标**：把搜索、个人看板和简历匹配组织为用户可执行的求职计划，而不替用户做不可逆决定。

- Agent 可根据用户意图调用搜索、收藏、截止提醒和匹配工具，生成“今日优先投递清单”“本周新增关注”“准备事项”与岗位比较；写入收藏或投递状态前必须展示拟执行动作并获得用户确认。
- 建立固定评测集，覆盖：岗位事实准确性、来源引用、待确认岗位处理、简历幻觉、隐私删除、工具参数越权、预算与延迟；每次提示、目录或模型版本升级前后比较结果。
- 提供运营观测：工具成功率、分类待确认率、模型调用次数/成本、用户撤销动作、匹配解释被质疑率；这些统计由程序计算，不由模型生成。
- **验收**：所有写操作有用户确认和审计；预算达到上限时停止付费步骤并返回可理解的状态；用户能区分“系统检索事实”“规则判断”“模型建议”。

#### 课程相关能力（可选未来方向）

大学课程、学习成果、课程—技能对比和课程推荐如在未来重新立项，应作为独立模块评估；它们不属于当前求职工作台对用户的承诺，也不限定职业目录为 IT 范围。

### 7.4 已知限制与后续确认

1. **更新判定边界**：已经确定链接变化、行号和排序不算新增；当前仍不对地点、届次、批次、公司名称或岗位文本的既有内容修改做更新/删除语义处理。实施中会以“不重复导入”为优先，不把这类变化自动解释为更新。
2. **运行入口与权限**：已确定通过仅绑定本机回环地址的管理 API 和前端“管理更新”入口运行；不建设公网写入 API 或普通用户上传入口。
3. **通知持久化位置**：已确定批次及处理记录持久化在本地数据层；通知已读/关闭状态只需在当前浏览器持久化。
4. **新增统计**：已确定通知主数量为新增原子岗位数，并补充涉及招聘记录数；归类、待确认、失败与主数量采用同一原子岗位口径。

## 8. 实现一致性原则

- 以原始招聘记录和来源 ID 为证据根；标准目录只描述分类，不替代原始招聘岗位标题。
- 目录映射、拆分、分类版本、批次和失败原因必须可追溯；不能在页面打开时运行模型或更改数据。
- 统计数量由已持久化记录确定，模型只能参与候选分类，不能生成或修改数量。
- 任何将来发现“代码存在但页面未接入”的能力，都必须在本文档标为“部分实现”或“未实现”，直到用户可验证其完整路径。
